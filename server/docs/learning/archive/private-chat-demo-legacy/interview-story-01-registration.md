# Issue 1：注册与验证码投递面试故事

## 1. 先说项目，不要先说故障

这是一个 Qt 客户端、C++ GateServer 和 Go VerifyServer 组成的本地在线私聊 Demo。
注册阶段使用 HTTP，验证码服务之间使用 gRPC，验证码放在 Redis，最终用户写入 MySQL。

这段介绍先建立上下文，面试官才知道后面的故障发生在哪条链路上。

```text
Qt
 └─ HTTP /get_verifycode
     └─ GateServer
         ├─ MySQL 只读查重
         └─ gRPC VerifyServer
             ├─ Redis 保存验证码 180 秒
             └─ QQ SMTP 异步发信

Qt
 └─ HTTP /user_register
     └─ GateServer
         ├─ Redis 校验验证码
         └─ MySQL reg_user 存储过程落库
```

## 2. 六十秒版本

我在一个 Qt 聊天 Demo 中负责跑通注册链路。最初前端显示验证码已发送，但用户收不到邮件；同时重复邮箱还可能得到错误的成功提示。

我先用真实 HTTP 请求建立回归，再按 GateServer、VerifyServer、Redis、SMTP 和邮箱逐层检查。数据库确认目标邮箱没有注册，所以排除了重复邮箱拦截。VerifyServer 生成验证码后，SMTP 日志报 `connection reset by peer`。

进一步检查发现 Clash TUN 把 SMTP 域名解析到了 Fake-IP，Go 的直接 TLS 连接无法完成握手。关闭 TUN 后，SMTP 日志出现成功，邮箱也收到了验证码。

在代码上，我把发送前的邮箱查重拆成独立只读查询，已注册邮箱返回 `1007`；注册提交仍保留 `reg_user` 存储过程作为最终防线。最后验证了新 User 落库、Qt 注册成功，以及重复邮箱不再写 Redis 或发信。

## 3. STAR 讲故事版本

### Situation：背景

注册流程由多个组件组成。Qt 只看到 GateServer 的 HTTP 响应，GateServer 还要调用 VerifyServer；验证码既要存 Redis，又要尝试通过 SMTP 发给用户。

问题出现时，界面显示“验证码已发送”，但邮箱没有收到。另一个问题是，重复邮箱的业务规则没有在发送验证码前明确拦截。

### Task：任务

我需要确认问题到底发生在业务判断、Redis 写入、gRPC 调用、SMTP 连接还是邮箱最终投递，并让重复邮箱在错误的阶段被拒绝。

同时不能为了前置查重而调用 `RegUser`，因为这个函数不是纯查询，它会执行注册存储过程。

### Action：行动

第一步，我把真实 HTTP `/get_verifycode` 作为测试入口，而不是只测单个函数。这样可以覆盖 Qt 之后的 GateServer、数据库和 VerifyServer 边界。

第二步，我查询数据库确认目标邮箱未注册，排除了 GateServer 返回 `1007` 的可能。随后查看 VerifyServer 日志，确认请求和验证码生成都发生了。

第三步，我检查 Redis 键和 TTL。验证码键的生命周期是 180 秒，所以 Redis 存在只能证明短时保存成功，不能证明邮件送达。

第四步，我检查 SMTP 错误。日志显示 QQ SMTP 465 连接被对端重置，随后用 DNS 和 TLS 握手命令复现，发现 `smtp.qq.com` 解析到了 `198.18.*` Fake-IP。

第五步，我关闭 Clash TUN 做单变量验证。关闭后邮件发送成功，邮箱实际收到验证码，说明根因在本地代理的 DNS/路由路径，而不是注册账号或邮箱地址。

第六步，我补上 `CheckEmailExists()`。它只执行参数化 `SELECT 1 ... LIMIT 1`，已注册邮箱返回 `1007`，查询异常返回 `1008`；只有 `NotFound` 才继续调用 VerifyServer。

第七步，我保留 `reg_user` 的最终检查。即使前置查询通过，如果并发请求在此期间先注册成功，存储过程仍返回重复结果，避免竞态造成脏数据。

### Result：结果

关闭 TUN 后，真实邮箱收到验证码，Qt 完成注册，MySQL 中出现新的 User，注册结果返回了新的 `uid`。

注册完成后再次请求验证码返回 `1007`，没有覆盖已有 Redis 验证码，也没有继续调用邮件服务。这个结果证明业务查重、验证码校验、SMTP 提交和数据库落库都通过了各自的验收点。

### Reflection：复盘

这次还暴露了异步发送的边界：当前 `SendMail()` 启动 goroutine 后，VerifyServer 立即返回成功；SMTP 失败只能异步写日志。因此当前的成功语义是“验证码写入 Redis，并启动发信任务”，不是“邮件已经送达”。

如果继续做生产化，我会增加 outbox 或消息队列、发送状态、重试和告警，并避免在日志和响应中输出密码。当前 Demo 只声明完成了单机注册基线，不声明可靠投递或高可用。

## 4. 面试追问卡

### Q：为什么网关要查邮箱，是否和用户服务耦合？

这不是把注册实现复制到网关，而是在现有教学架构中增加一个发送前的业务前置条件。查询被封装在 `MySQLManager::CheckEmailExists()` 中，GateServer 只消费 `NotFound/Exists/QueryFailed` 结果。

真正的注册仍由 `reg_user` 负责，网关的查询不能替代数据库最终防线。后续拆成独立 UserService 时，可以把这个查询和注册能力一起迁移，HTTP 错误契约保持不变。

### Q：为什么不直接调用 `RegUser` 查重？

因为 `RegUser` 会执行存储过程并可能插入 User，它是有副作用的命令，不是查询。发送验证码前调用它会把“检查邮箱”错误地变成“提前注册”。所以前置使用只读 SQL，提交注册时再使用 `RegUser`。

### Q：`1007` 和 `1004` 有什么区别？

`1007` 发生在发送验证码前，表示邮箱已经注册，因此不应该发信。`1004` 发生在验证码校验通过、执行最终注册时，表示用户名或邮箱重复，是存储过程的最终兜底结果。

### Q：为什么接口返回成功，用户还是收不到邮件？

因为当前邮件发送是异步的。接口只等待 Redis 写入成功，然后启动 SMTP goroutine；SMTP 连接失败发生在响应返回之后。必须分别观察 Redis、SMTP 提交日志和邮箱，而不能只看 HTTP `error: 0`。

### Q：你怎么证明是 Clash TUN，而不是 QQ 邮箱拒收？

日志中的错误发生在 SMTP TLS 连接阶段，还没有进入认证和收件人投递阶段。开启 TUN 时域名解析到了 `198.18.*` Fake-IP，465 握手超时或重置；只关闭 TUN 后 SMTP 成功且邮箱收到，单变量结果支持代理 DNS/路由是根因。

### Q：这个实现还有什么不足？

异步发信没有重试和可查询状态，SMTP 接受也不等于最终到达；日志和注册响应还需要清理敏感字段；MySQLPool 的线程安全和退出流程也要专项修复。这些都不影响本次单机 Issue 1 验收，但不能被包装成生产级能力。

## 5. 结尾怎么收束

我会把这个问题总结为：先用真实调用链建立可复现证据，再用分层日志区分业务拒绝、Redis 保存、SMTP 提交和最终投递；修复时把有副作用的注册命令和发送前的只读查重分开，最后用真实邮箱、数据库结果和重复请求回归共同验收。

这句话能同时体现排障方法、边界意识、数据一致性和对系统限制的诚实判断。
